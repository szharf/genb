# 管理端 Docker 大文件上传修复部署记录

日期：2026-09-04

## 问题与根因

- 新前端服务器对 `100 MiB + 1 byte` 的 Docker 上传请求直接返回 HTTP 413，因此所谓“超过 1G 上传失败”实际在 100 MiB 就会发生。
- 后端虽然已配置 5 GB 上限并使用 `transferTo`，但前端 Nginx 的 server 级上限仍为 100 MiB。
- Nginx 默认会把完整请求体缓存在前端磁盘；后端 multipart 默认暂存在 `/tmp`，而 47 服务器的 `/tmp` 是内存型 `tmpfs`，大文件会放大磁盘和内存风险。

## 修改范围

- 仅为 `/genb/api/v1/deploy/upload` 新增精确 Nginx location：网关上限 `5g`、请求和上游超时一小时、`proxy_request_buffering off`。
- 同步 IP 入口、`alaya.to`、`genesis-engine.ai` 和本地 Compose Nginx 基线。
- Spring multipart 临时目录增加 `GENB_UPLOAD_TMP_DIR` 配置；生产值为 `/app/gen-b-console/upload-tmp`。
- 普通 `/genb/api/` 与其他项目路由不放宽，仍受 100 MiB 限制。
- 未修改上传业务逻辑，未上传或导入真实镜像，未部署核心组件模型。

## 验收结果

| 验收项 | 结果 |
|---|---|
| 三个入口的上传边界 | IP、`alaya.to`、`genesis-engine.ai` 的 `1 GiB + 1 byte` 无文件体声明请求均不再被 Nginx 返回 413，已到达后端 |
| 上传最大边界 | `5 GiB + 1 byte` 由 Nginx 返回 413，未发送请求体 |
| 普通 API 边界 | `/genb/api/v1/agents` 的 `100 MiB + 1 byte` 声明请求仍返回 413 |
| 后端健康 | `8581/api/actuator/health` 与前端健康代理均返回 `200 UP` |
| 临时目录 | 进程已加载 `/app/gen-b-console/upload-tmp`，验收后文件数为 0 |
| 既有入口 | GenB 管理端、客户端、统一登录、GenO、GenC、FIBO、Alaya.To 官网和 Genesis Engine.AI 官网均返回 200 |

边界探针只发送 `Content-Length` 和 `Expect: 100-continue`，不传输实际大文件，因此到达后端后会因不完整 multipart 请求返回业务异常；该探针只用于证明 Nginx 上限和路由边界，不作为真实上传业务结果。真实用户上传仍受网络稳定性影响，当前不支持断点续传。

## 回滚

1. 恢复前端备份中的 `frontends.conf` 和 `shared-platform-routes.conf`，执行 `nginx -t` 后 reload。
2. 停止 GenB 后端，恢复后端备份中的 JAR 与 `genesis.env`，再执行 `/app/gen-b-console/start.sh`。
3. 以 `127.0.0.1:8581/api/actuator/health` 验证回滚结果。
