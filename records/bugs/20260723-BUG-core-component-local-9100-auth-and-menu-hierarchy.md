# 核心组件本地9100鉴权与菜单层级错误

## 现象

1. 从本地客户端进入 `http://localhost:9100/genb/core-components` 后，页面显示“核心组件目录加载失败”；网络面板中 `GET http://localhost:9100/api/v1/core-components` 返回 HTTP 403。
2. “智能体中心”和“核心组件”被实现为两个并列一级菜单；正确结构应为“智能体中心”父菜单，下设“智能体列表”和“核心组件”。

## 最小复现

1. 在 `localhost:9100` 登录管理员账号，只保留客户端真实写入的 `genb-client-token`，确保旧管理端键 `token` 不存在。
2. 打开 `/genb/core-components`。
3. 修复前，真实 Chrome 捕获目录请求 HTTP 403，页面显示加载失败；同一 Token 显式放入 Authorization 请求头时接口返回 HTTP 200 和14条。

## 原因

- 本地9100由 `gen-b-client` Vite提供；它把 `/genb` 代理到9000管理端，使两个前端共享9100同源的 `localStorage`。
- 客户端登录将JWT写入 `genb-client-token`，但核心组件以及多数管理端API只读取旧键 `token`，因此从客户端进入管理端后请求没有携带Bearer Token，后端按权限规则返回403。
- 菜单问题来自 `MainLayout.vue` 将两个路由声明为并列 `el-menu-item`，且原智能体页面仍使用“智能体中心”作为自身标题。

## 修复方案

- 新增统一的管理端Token解析函数：优先读取当前客户端键 `genb-client-token`，兼容旧管理端键 `token`。
- 核心组件、智能体、驾驶舱、监控、Genesis权限和上传请求统一使用该解析函数，避免相同403在其他管理页重复出现。
- 新增Token键优先级回归测试。
- 固定“智能体中心 → 智能体列表、核心组件”父子关系，并增加导航结构测试。

## 验证结果

- 修复前真实Chrome：仅存在 `genb-client-token` 时，目录HTTP 403、失败提示可见。
- 修复后同一真实Chrome场景：目录HTTP 200、返回14条、失败提示消失。
- Token解析、导航、目录和详情模型测试通过。
- 管理端中文、英文生产构建通过。
- 本任务只涉及本地开发，不需要也未执行部署。

## 诊断纠正

第一轮验证错误地打开了9000管理端，并把另一个公网404当成用户报告的问题。用户明确实际地址后，已改用9100同源入口重新建立浏览器反馈环；最终根因是本地Token键不一致，公网404与本次403无关。

## 是否需要回归测试

需要。客户端登录进入管理端时，应在仅存在 `genb-client-token` 的新浏览器上下文中验证智能体列表、核心组件、驾驶舱、监控和管理上传请求均携带Authorization。
