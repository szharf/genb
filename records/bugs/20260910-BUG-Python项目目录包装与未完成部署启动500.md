# Python 项目目录包装与未完成部署启动 500

日期：2026-09-10。实例：`7783d566-69db-4371-827b-12ab69d5c5c1`，node18，端口 18001。

## 根因

用户上传 ZIP 内为 `fibo_refactor/server.py`，部署入口填写 `server.py`。节点原程序只在 ZIP 根目录查找入口，返回 `Python entry point is missing at ZIP root`；尚未创建 systemd 服务。平台仍允许点击启动，远端执行启动不存在的服务，IOException 未转为业务错误，形成 HTTP 500。浏览器 `127.0.0.1:7897` 是本机代理，与此故障无关。

## 平台修复

- 同时支持根目录代码和仅包裹一个项目文件夹的 ZIP。优先精确根目录入口；只有唯一项目文件夹且入口存在时才选取内层目录，不递归猜测多个项目。
- SCRIPT 与 ASGI 共用项目根目录选择；requirements.txt、模板、业务代码一起移动到工作目录。
- 节点 inspect 返回 startable；Python 以对应 systemd unit 是否存在判定，Docker 以容器是否存在判定。服务未创建时不调用 systemctl start。
- 后端启动前核对远端实际状态，不可启动时返回 409 和具体提示，不再对本例返回 500。
- 保留两轮此前 CORS 和节点检查过期修复。

## 验证与实际恢复

- 节点 8 项测试通过：两种 ZIP 布局、SCRIPT/ASGI、歧义拒绝、未创建服务不调用 systemctl，以及原有路径穿越、校验和、Docker 策略测试。
- 后端 206 项，0 失败、0 错误、1 跳过，包含启动未准备完成实例的错误响应测试。
- 现场核验确认原实例没有 work 目录和 systemd unit，备份原失败现场后使用原材料、原实例 ID 恢复准备，没有创建重复实例。
- 恢复依赖安装时，owlready2 源码构建分别触及 192/256 MiB 限制；没有取消内存保护或给 18 安装 Docker。
- 在 47 的隔离用户/受限 systemd 构建环境生成 owlready2 0.51 wheel，再经受限节点上传通道送到 18 并校验 SHA256。此为本次运维恢复辅助，不表示平台已实现自动跨节点构建依赖。
- 完整依赖批量安装还触及过 256 MiB 限制，后续使用预构建包并关闭安装阶段字节码预编译继续恢复。失败日志保留，未把中途失败记为成功。

用户原始本地项目和已上传 ZIP 保持原样。实际发布文件、现场备份和最终恢复结果见同名部署记录。
